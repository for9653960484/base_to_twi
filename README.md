# Base To — Система управления базой знаний по техобслуживанию парка оборудования

Модульная платформа для управления базой технологических карт, листов по технике безопасности, инструкций по выполнению работ, материалами TWI-обучения и матрицей компетенций технического персонала.

### Отработанные блоки (подробно)

#### База оборудования (`/equipment`)

- Каталог оборудования: название, серийное название, описание, `custom_attributes` (JSONB)
- API: список с пагинацией и поиском, создание, чтение, обновление, счётчики связей
- Роли: создание/редактирование — `admin`, `park_owner`; просмотр — все авторизованные
- UI: таблица, форма создания/редактирования, фильтр «только активные»

#### Заводская документация (`/documents`)

- Загрузка файлов (PDF, DOCX, DOC, TXT, MD) с привязкой к `equipment_id`
- Хранение по каталогу: `storage/documents/{equipment_id}/{document_id}/v{N}/`
- Версионирование: `document_versions`, история изменений
- Workflow статусов: `draft` → `pending_approval` → `published` → `archived`
- API: upload, download, список с фильтрами, новая версия, submit/approve/archive, удаление
- UI: таблица, форма загрузки, фильтр по оборудованию, скачивание, кнопка «Удалить»
- Удаление (`DELETE /api/v1/documents/{id}`, роли `admin`, `park_owner`, `mentor`) снимает карточку и вместе с ней:
  - файл документа и все версии с диска (`storage/documents/{equipment_id}/{document_id}/`);
  - результат AI-оцифровки — фрагменты и векторы в `knowledge_chunks`;
  - записи задач AI по этому документу в `ai_tasks`.
- Технологические карты и листы техники безопасности, уже созданные из документа, остаются; у них обнуляется `source_document_id`.

#### AI-обработка документов

Пайплайн (Celery worker, задача `document_pipeline`):

1. Извлечение текста из файла (PDF/DOCX/TXT)
2. Разбиение на chunks и векторизация (embeddings → `knowledge_chunks`)
3. LLM-анализ: регламентные работы, меры безопасности, инструменты, резюме
4. Обновление `documents.ai_processing_status` и журнала `ai_tasks`

Все модели задаются в `.env` (см. раздел [Конфигурация AI](#конфигурация-ai)).

- Запуск: кнопка «AI-обработка» в UI или `POST /api/v1/documents/{id}/ai-process`
- Статусы: `pending` → `processing` → `completed` / `failed`
- UI: баннеры при старте/завершении/ошибке, авто-обновление списка (polling), повтор при ошибке
- Требования: Redis (порт 6379) и Celery worker; при недоступности Redis — быстрый ответ 503
- Отдельные задачи воркера поверх уже проиндексированного текста:
  - `extract_maintenance` — технологические карты (ежедневное, еженедельное, ежемесячное, квартальное, полугодовое и годовое ТО). В длинном руководстве в модель уходят главы с графиком обслуживания, а не только начало файла
  - `extract_safety` — лист техники безопасности: СИЗ и условия работы, только то, что явно есть в документе

#### Справочная система (`/knowledge`)

- Векторный поиск по проиндексированным фрагментам документов (pgvector; без расширения — ограниченный режим)
- Генерация ответа через LLM с опорой на найденный контекст
- Фильтр по `equipment_id` в API и UI
- UI: выбор оборудования, поле вопроса, ответ с перечнем источников

#### Технологические карты (`/tech-cards`)

- Каталог регламентных работ по видам ТО: от ежедневного до годового. Создание — на `/tech-cards` по документу с завершённой AI-оцифровкой; в карту попадает только регламент из текста
- Привязка к `equipment_id`, workflow статусов (`draft` → `pending_approval` → `published` → `archived`). Новые карты сохраняются как черновик
- API: список с фильтрами (`equipment_id`, `maintenance_type`, `status`), CRUD, экспорт `GET /api/v1/tech-cards/export/{id}?format=pdf|docx`
- PDF доступен и для черновика: открывается в браузере, файл можно сохранить. Оформление как у листа безопасности — корпоративный DOCX (`template_type=tech_card`) со страницы «Документы» либо письмо на корпоративном бланке. В документе всегда указано оборудование, вид ТО и перечень работ. Поля шаблона: `{{EQUIPMENT_NAME}}`, `{{TITLE}}`, `{{MAINTENANCE_TYPE}}`, `{{GENERATED_AT}}`, `{{WORK_ITEMS_BLOCK}}`
- UI: выбор оборудования → документ → «Создать тех. карты»; таблица (название, готовность, «Скачать PDF»). Текста карты на странице нет
- Демо-данные: `scripts/seed_tech_cards.py` (шаблон брендбука + карты по всем видам ТО для каждой единицы оборудования)

#### Техника безопасности (`/safety`)

- Лист по оборудованию: набор СИЗ (название, назначение, обязательность) и условия работы (температура, влажность, напряжение и прочие параметры из документа)
- Источник — документ с завершённой AI-оцифровкой; извлекается только то, что явно есть в тексте
- API: `GET /api/v1/safety`, `POST /api/v1/safety/generate`, `GET /api/v1/safety/generate/{document_id}/status`, `GET /api/v1/safety/export/{id}` (PDF)
- PDF: корпоративный DOCX-шаблон (`template_type=safety_sheet`), загружается на странице «Документы». Поля: `{{EQUIPMENT_NAME}}`, `{{TITLE}}`, `{{GENERATED_AT}}`, `{{PPE_BLOCK}}`, `{{CONDITIONS_BLOCK}}`, `{{NOTES}}`. Если шаблона нет — письмо на корпоративном бланке. В листе всегда указано оборудование
- UI: список готовых листов (название, оборудование, «Редактировать», «Скачать PDF»). Реквизиты — название, оборудование, СИЗ, условия и правила — правятся в форме, как карточка оборудования; на странице текст листа не показывается
- Хранение: `safety_sheets`. При удалении документа ссылка `source_document_id` обнуляется, лист остаётся

#### Общая инфраструктура

- **БД**: `database/init/` (Docker) + `database/schemas/` (локально без pgvector); `scripts/init_database.py` выбирает схему автоматически
- **pgvector (Windows)**: `scripts/windows/*.cmd` и `scripts/install_pgvector_windows.ps1`, `enable_pgvector.py`
- **Backend**: модульный FastAPI, JWT/RBAC, dev-режим без токена (`APP_ENV=development`)
- **Frontend**: React + Vite, локализация RU/EN, React Query
- **Docker Compose**: развёртывание на сервере (postgres, redis, backend, ai-service, worker, frontend)

### Слои системы

| Слой | Технологии | Назначение |
|------|-----------|------------|
| База данных | PostgreSQL 16 + pgvector | Хранение сущностей, JSON-атрибуты, версионирование, векторный поиск |
| Backend | Python 3.12, FastAPI, SQLAlchemy, Alembic | REST API v1, RBAC, интеграции HR/AI |
| AI Service | Celery, Redis, LLM-провайдеры | Асинхронная обработка документов, генерация инструкций/TWI |
| Frontend | React 18, Vite, TypeScript, i18next | Адаптивный UI для ролей: админ, владелец парка, наставник, техник, HR |

### Функциональные модули

- **База оборудования** — каталог оборудования с настраиваемыми полями
- **База знаний (AI)** — заводская документация, векторный Q&A-поиск
- **Технологические карты** — регламентные работы (годовое → ежедневное ТО), статусы готовности, PDF на бланке или по корпоративному шаблону
- **Техника безопасности** — лист СИЗ и условий работы по оборудованию, правка реквизитов, PDF на бланке или по корпоративному шаблону
- **Календарь ТО** — сводный график на дату
- **Инструкции ТО** — шаги / ключевые моменты / причины, версионирование
- **Курсы обучения (TWI)** — генерация из утверждённых инструкций
- **Матрица компетенций** — навыки, уровни, привязка к оборудованию и сотрудникам
- **HR-интеграция** — импорт сотрудников, ролей, подразделений
- **Администрирование** — пользователи, роли, словари, интеграции

### Доменные связи

```
Оборудование ↔ Документы ↔ Тех. карты и листы безопасности
Оборудование ↔ Документы ↔ Инструкции ↔ TWI-курсы ↔ Компетенции ↔ Сотрудники
```

### Роли пользователей

| Роль | Доступ |
|------|--------|
| `admin` | Полный доступ, настройки системы |
| `park_owner` | Управление парком оборудования, утверждение документов |
| `mentor` | Редактирование инструкций, курсов, оценка компетенций |
| `technician` | Просмотр инструкций, прохождение курсов |

## Локальная разработка (без Docker)

Основной способ разработки на рабочей машине. Подробно: **[docs/local-development.md](docs/local-development.md)**.

```powershell
# Важно: команды выполняются из КОРНЯ репозитория base_to_twi, не из backend/

cd C:\Users\Дима\Documents\ALEX\PROJECTS\base_to_twi

# 1. Настройка (venv, npm, .env)
.\setup.ps1
# или: .\scripts\setup.ps1

# 2. PostgreSQL + Redis должны быть запущены локально

# 3. Схема БД (один раз)
.\.venv\Scripts\python.exe scripts\init_database.py

# 3a. (опционально) Демо технологические карты и шаблон брендбука
.\.venv\Scripts\python.exe scripts\seed_tech_cards.py

# 4. Запуск (4 сервиса)
.\dev-all.ps1
# или: .\scripts\dev-all.ps1
```

> **Redis** нужен для AI-обработки документов: `docker compose up -d redis` или локальный экземпляр на порту 6379.  
> **PostgreSQL**: в `.env` по умолчанию порт `5433` (локальная установка). Данные сохраняются между перезапусками — `init_database.py` не очищает БД.

| Сервис | URL |
|--------|-----|
| Frontend | http://localhost:5173 |
| Оборудование | http://localhost:5173/equipment |
| Документы | http://localhost:5173/documents |
| Тех. карты | http://localhost:5173/tech-cards |
| Техника безопасности | http://localhost:5173/safety |
| Справка (Q&A) | http://localhost:5173/knowledge |
| Backend API | http://localhost:8000/docs |
| AI service | http://localhost:8001/health |
| Celery worker | отдельное окно (AI-обработка) |

Зависимости Python: корневой `requirements.txt` (агрегирует `backend/` + `ai-service/`).

## Развёртывание на сервере (Docker)

Прод: образы собираются в GitHub Actions и пушатся в GHCR; на сервере — `docker-compose.prod.yml`.  
Подробно: **[docs/deployment.md](docs/deployment.md)**.

```bash
cp .env.example .env
# Настроить продакшен-секреты и AI-ключи
# После push в main (или docker login + pull):
docker compose -f docker-compose.prod.yml up -d
```

Схема БД применяется при первом запуске `postgres` из `database/init/`.

| Сервис | Порт на сервере (хост) |
|--------|------------------------|
| Frontend | 5173 |
| Backend | **8010** |
| AI service | **8002** |
| PostgreSQL / Redis | только внутри Docker (не снаружи) |

## API

- **Backend**: `GET /api/v1/health` — проверка состояния
- Версионирование: `/api/v1/...`
- OpenAPI: `/docs`, `/redoc`

Основные группы endpoints:

**Реализованы:**
- `/api/v1/equipment` — оборудование (CRUD, связи)
- `/api/v1/documents` — документация (upload, download, версии, workflow, AI, удаление вместе с файлом и AI-оцифровкой)
- `/api/v1/knowledge` — Q&A поиск по базе знаний
- `/api/v1/tech-cards` — технологические карты (список, CRUD, экспорт PDF/DOCX)
- `/api/v1/safety` — техника безопасности (СИЗ и условия работы по оборудованию)
- `/api/v1/ai` — статус AI-задач, callback

**Каркас (маршруты объявлены):**
- `/api/v1/maintenance-calendar` — календарь ТО
- `/api/v1/instructions` — инструкции ТО
- `/api/v1/courses` — TWI-курсы
- `/api/v1/competencies` — матрица компетенций
- `/api/v1/users`, `/api/v1/roles` — управление доступом
- `/api/v1/hr` — HR-интеграция
- `/api/v1/brandbook` — корпоративные DOCX-шаблоны тех. карты и листа техники безопасности; загрузка и образец — на странице «Документы»

## Конфигурация AI

Все модели задаются в `.env` (см. `.env.example`):

| Переменная | Назначение |
|------------|------------|
| `AI_PROVIDER` | `external` / `local` / `hybrid` |
| `AI_EXTERNAL_MODEL` | Тяжёлая LLM (анализ документов, Q&A) |
| `AI_LIGHT_MODEL` | Лёгкая LLM (рутинные задачи) |
| `AI_LOCAL_HEAVY_MODEL` | Локальная тяжёлая модель (Ollama) |
| `AI_LOCAL_LIGHT_MODEL` | Локальная лёгкая модель |
| `AI_EMBEDDING_MODEL` | Модель эмбеддингов (внешняя) |
| `AI_EMBEDDING_LOCAL_MODEL` | Локальная модель эмбеддингов |
| `AI_QA_MODEL` | Модель для справочной системы (пусто = `AI_EXTERNAL_MODEL`) |
| `VECTOR_DIMENSION` | Размерность векторов (1536 для OpenAI, 768 для nomic-embed-text) |

Пример для **OpenAI**:
```env
AI_PROVIDER=external
AI_EXTERNAL_API_KEY=sk-...
AI_EMBEDDING_PROVIDER=external
VECTOR_DIMENSION=1536
```

Пример для **Ollama** (on-prem):
```env
AI_PROVIDER=local
AI_LOCAL_HEAVY_MODEL=llama3.1:70b
AI_EMBEDDING_PROVIDER=local
AI_EMBEDDING_LOCAL_MODEL=nomic-embed-text
VECTOR_DIMENSION=768
```
